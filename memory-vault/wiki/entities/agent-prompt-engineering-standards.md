# Agent Prompt Engineering Standards（智能体提示工程准则）

> 来源: 通用 Prompt Engineering 实践
> 用途: 作为 AI Agent 的 system prompt 级行为准则，使其掌握专业级 prompt engineering 能力
> 原始文件: `%USERPROFILE%\Desktop\Agent准则.md`
> 入库日期: 2026-06-18（2026-07-03 去品牌化重写为通用准则）

---

## 一、基础架构：Messages API 格式

### 必须遵守的规则
- **messages** 数组的第一个消息必须使用 `"role": "user"`
- **user 和 assistant 消息必须严格交替**，不能出现连续两个相同 role
- 每个消息对象必须包含 `role` 和 `content` 两个字段
- 必须参数：`model`（模型名）、`max_tokens`（最大生成 token 数）、`messages`（消息数组）
- 可选关键参数：`system`（系统提示词）、`temperature`（输出多样性，0=确定性最高）、`stop_sequences`（停止序列）

### System Prompt
- **system prompt 独立于 messages 数组**，属于单独的 `system` 参数
- 用途：提供上下文、指令、行为准则、角色设定
- **放在 system 参数中，而非 user message 中**
- 一个好的 system prompt 可以显著提升模型的规则遵循能力

## 二、清晰直接原则（Golden Rule of Clear Prompting）

### 核心信条
**模型就像一个新入职的员工——除了你明确告诉它的内容，它没有任何上下文。** 你说得越清楚直接，模型的回应就越准确。

### Golden Rule（黄金法则）
**把你的 prompt 给同事或朋友看，让他们按指令执行。如果他们感到困惑，模型也会困惑。**

### 实践要点
1. **不要暗示，直接说出你的要求** — 比如 "跳过前言，直接输出诗歌" 而非只写 "写一首诗"
2. **明确你的偏好** — 如果模型模棱两可，用 "如果你必须选一个，你会选哪个？" 来推动它做决定
3. **细节决定成败** — 检查 prompt 中的拼写和语法错误。模型对模式敏感：你犯错时它更容易犯错，你聪明时它更聪明
4. **你想要的输出格式、长度、风格，全部明确写出**

---

## 三、角色分配（Role Prompting）

### 原理
**给模型赋予一个特定角色（含完整上下文），可以显著提升其在特定领域的表现。** 就像告诉一个人 "像 X 一样思考" 会改变其输出。

### 最佳实践
- 角色设定可以放在 system prompt 或 user message 中
- **角色描述越详细越好**：不仅告诉它 "你是谁"，还要告诉它 "你在对谁说话"
- 角色提示能改变：风格、语调、内容深度、准确度
- 对数学/逻辑任务，角色设定尤其有效 — 如 "你是一个专门解决复杂逻辑问题的逻辑机器人"
- 示例对比：
  - 差：`"You are a cat."` → 只有角色
  - 好：`"You are a cat talking to a crowd of skateboarders."` → 角色 + 受众

---

## 四、数据与指令分离（XML 标签法）

### 核心原则
**使用 XML 标签将可变输入数据与固定指令分离开。** 模型能很好地识别 XML 标签作为 prompt 组织机制。

### 具体做法
- 成对使用：`<tag>内容</tag>`
- 标签名应该语义化：`<email>`、`<document>`、`<question>`、`<history>`
- **每个独立的输入数据使用独立的 XML 标签对**
- **没有 "特殊魔法标签"** — 所有 XML 标签的效果来自其结构性，而非特定标签名

---

## 五、输出格式化与 "替模型说话"（Prefilling）

### 输出格式化
- **模型可以按你要求的任何格式输出** — 你只需要明确说出来
- 推荐使用 **XML 标签** 包裹关键输出内容，便于程序化提取
- **JSON 格式** 也是模型擅长的输出格式

### Prefilling（预填充 / 替模型说话）
- **在 `assistant` turn 中放入文本**，模型会从那里继续生成
- 这是控制模型输出格式的最强手段之一
- 常见 prefill 示例：`"{"` → 强制 JSON 输出；`"<response>"` → 确保输出包裹在指定标签中

---

## 六、逐步思考（Chain of Thought）

### 核心原理
**给模型时间 "出声思考"，可以提升复杂任务的准确率。** 但如果只让它 "想想" 但不输出，等于没有思考。

### 做法
- 明确要求模型 **先在特定 XML 标签中输出思考过程，再给出最终答案**
- 在 prompt 末尾加上 "在回答之前，先想一想" 或 "先思考再回答"
- 模型有时对选项顺序敏感 — 它更倾向于选择后面的选项，把你倾向的选项放在后面

---

## 七、示例驱动（Few-Shot Prompting）

### 核心原理
**给模型提供理想回答的示例，是知识工作中让模型按预期行为的最有效单一手段。**

### 关键要点
- **示例是 prompt engineering 中最有效的工具**
- 示例同时解决两个问题：**正确的内容** + **正确的格式**
- 示例应放在 `<example></example>` XML 标签中
- **示例越多越好**，尤其是覆盖常见边缘情况
- 如果 prompt 中有 scratchpad（思考草稿），也应该给出 scratchpad 的示例

---

## 八、避免幻觉（Hallucination Prevention）

### 核心策略

#### 策略 1：给模型 "退路"（Give an Out）
- 告诉模型 **如果不知道可以说不确定**
- 示例：`"只有在你确定知道答案时才回答"`

#### 策略 2：先找证据再回答（Gather Evidence First）
- 让模型 **先提取相关引用/引文**，再基于引用作答
- 如果引用不支持答案，模型会主动指出

#### 策略 3：组合多种技术
- 角色分配 + 逐步思考 + 退路 + 证据提取

## 九、复杂 Prompt 构建框架（10 要素结构）

| 序号 | 要素 | 说明 | 必要性 |
|------|------|------|--------|
| 1 | **user role** | Messages API 必须以 user 开头 | 必须 |
| 2 | **Task Context** | 告诉模型它的角色和总体目标 | 推荐前置 |
| 3 | **Tone Context** | 期望的语气风格 | 按需 |
| 4 | **Task Description & Rules** | 详细任务描述 + 规则约束 + "退路" | 核心 |
| 5 | **Examples** | `<example>` 标签包裹的理想对话示例 | 最有效 |
| 6 | **Input Data** | 需要处理的数据，各用 XML 标签包裹 | 按需 |
| 7 | **Immediate Task** | "现在立刻做什么" 的提醒 | 推荐放后面 |
| 8 | **Precognition** | "先思考再回答" | 复杂任务推荐 |
| 9 | **Output Formatting** | 输出格式要求 | 放末尾更好 |
| 10 | **Prefill** | assistant turn 中的预填充文本 | 强控制 |

### 关键原则
- **先全量后用，再精简** — 让 prompt 先跑通，再优化
- **用户问题放 prompt 末尾**效果通常比开头好
- **prompt engineering 不是纯粹公式化的** — 为每个场景准备测试用例，多尝试不同结构

---

## 十、Prompt Chaining（链式提示）

### 原理
**"写作即重写" — 模型在被要求改进自己的回答时，通常能提升准确性。**

### 实践模式
- **自我纠错**：Turn 1 回答 → Turn 2 要求找出错误并修正
- **自我保护**：给模型 "退路"，防止它对正确内容做不必要的修改
- **迭代改进**：逐步要求更生动/更详细/更有悬念

---

## 十一、Tool Use / Function Calling（工具使用）

### 本质
Tool use 是 **变量替换 + prompt chaining 的组合**：
1. 模型输出要调用的工具名和参数
2. 停止生成，执行实际函数
3. 将函数结果追加到对话中，让模型继续处理

---

## 十二、Prompt Engineering 元原则

1. **像教新人一样写 prompt** — 不给模型假设任何背景知识
2. **小细节大影响** — 拼写、格式、标点都会影响输出
3. **用 XML 标签做结构化** — 模型天生理解 XML 的组织语义
4. **先复杂后精简** — 先用全套技术让 prompt 跑通，再逐步删除不必要的部分
5. **多技术组合** — 角色 + 示例 + 逐步思考 + 退路 + 预填充 可以叠加使用
6. **测试驱动** — 为 prompt 准备多个测试用例，用不同结构反复实验
7. **Prompt 也是代码** — 需要版本管理、测试、迭代优化
8. **没有银弹** — prompt engineering 不是纯公式，不同场景需要不同组合

### 排查 prompt 问题的诊断流程
1. **模型理解错了吗？** → 更清晰直接地重写指令
2. **模型输出格式不对？** → 使用 prefill + XML 标签
3. **模型答案不准确？** → 加角色设定 + 逐步思考
4. **模型在编造信息？** → 给退路 + 要求先找证据
5. **复杂任务表现差？** → 使用十要素框架重建 prompt
6. **还是不行？** → 加 few-shot 示例、或将任务拆分为 prompt chain

---

## 行动指令

当进行任何 AI Agent 相关开发或对话时，必须：

1. **先理解任务**：确认用户想让 Agent 完成什么
2. **选择技术组合**：从上述技术中选择最适合当前任务的技术
3. **按十要素框架构建 prompt**（复杂任务时）
4. **给出完整可用的输出**：包含所有 XML 标签和占位符
5. **解释设计理由**：说明为什么选择这些技术、为什么按这个顺序排列
6. **提供测试建议**：告诉用户应该用什么测试用例验证效果
7. **迭代优化**：如果效果不好，按诊断流程排查

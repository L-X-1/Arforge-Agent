# Arforge 依赖归属与许可文件处理策略

审计日期：2026-07-28

## 当前事实

目标源码根目录没有第一方 `LICENSE`。当前工作区的 1,643 个 `LICENSE*` 文件
全部来自可再生成或第三方内容：

| 来源 | 数量 | 处理原则 |
| --- | ---: | --- |
| `node_modules` | 1,422 | 不提交源码仓库；需要依赖时由锁文件重装；分发依赖时保留所需通知 |
| `.venv` | 200 | 不提交源码仓库；由 Python 锁定依赖重建 |
| 下载的 Go 工具链 | 21 | 工具链整体可清理并重新下载，不单独删除其许可证 |
| 第一方源码 | 0 | 无待删除的第一方根许可证 |

## 不变量

1. 品牌清理不能删除第三方版权或许可通知。
2. `node_modules`、`.venv` 和下载工具链应作为整体生成物管理，不逐个改写。
3. 私有使用不等于取得第三方代码版权；未来对外分发前必须重新生成依赖清单和
   SBOM，并按实际分发内容汇总 NOTICE。
4. 如果某段上游代码被保留在第一方源码中，即使文件名、结构和品牌都已改变，
   仍按该代码实际许可证履行通知义务。
5. 删除任何依赖目录前，先验证锁文件、离线恢复能力和当前运行进程；删除属于
   独立的可恢复清理动作，不与产品品牌审计混用。

当前框架逐文件对账还明确排除了来源中的根 `LICENSE`、两个 vendored 包
`LICENSE` 和 `THIRD_PARTY_NOTICES.md`；它们没有复制到目标第一方源码。这个
事实只说明当前私有源码树的边界，不授权在分发第三方依赖时省略其许可通知。

## 推荐执行方式

- 开发仓库：忽略生成依赖目录，只保留锁文件和私有第一方声明。
- 私有部署：只复制运行所需文件，并在制品层生成第三方依赖清单。
- 将来开源：为 Arforge 自有代码选择独立许可证，同时保留实际复用第三方代码的
  通知；不要用删除 LICENSE 的方式声称来源变化。
